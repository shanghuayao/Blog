# Redis 滑动窗口算法

基于 Redis 实现滑动窗口（Sliding Window）限流算法，核心目的是解决传统“固定窗口算法”在临界点突发流量（临界双倍均值问题）上的缺陷。  
在 Redis 中，主要有两种实现思路：**基于有序集合（ZSet）的精确滑动窗口**，以及**基于计数器加权估算的近似滑动窗口**。两者在精度、性能和资源消耗上有着显著的权衡（Trade-off）。

## 方案一：基于 Redis ZSet 的精确滑动窗口（Sliding Window Log）
这是最经典、最直观的实现方式。利用 Redis 的 Sorted Set（ZSet），将请求的**毫秒时间戳**作为 score 和 member 存储。

### 实现逻辑
每次请求到来时（假设限制：最近 60 秒内最多 100 次）：

1. 移除 ZSet 中所有时间戳小于 当前时间 - 60秒 的旧数据（ZREMRANGEBYSCORE）。  
2. 统计当前 ZSet 中的元素总数（ZCARD）。  
3. 如果元素总数小于阈值 100：  
   * 将当前请求的时间戳加入 ZSet（ZADD）。  
   * 放行请求。  
4. 如果元素总数大于等于 100：  
   * 拒绝请求。

为了防止并发竞争导致的脏数据，上述操作必须封装在 **Lua 脚本** 中执行以保证原子性：

```lua
-- KEYS[1]: 限流key (如 rate_limit:user123)  
-- ARGV[1]: 当前毫秒时间戳  
-- ARGV[2]: 窗口大小(毫秒)  
-- ARGV[3]: 窗口内最大允许请求数

local key = KEYS[1]  
local now = tonumber(ARGV[1])  
local window = tonumber(ARGV[2])  
local max_limit = tonumber(ARGV[3])  
local clear_before = now - window

-- 1. 移除过期记录  
redis.call('ZREMRANGEBYSCORE', key, '-inf', clear_before)

-- 2. 统计当前窗口请求数  
local current_requests = redis.call('ZCARD', key)

-- 3. 判断并写入  
if current_requests < max_limit then  
    -- 使用 毫秒时间戳+随机串/序列号 作为 member 避免同一毫秒覆盖  
    redis.call('ZADD', key, now, now .. ':' .. redis.call('INCR', key .. ':seq'))  
    -- 设置 key 过期时间，避免冷数据长期占用内存  
    redis.call('PEXPIRE', key, window)  
    return 1 -- 放行  
else  
    return 0 -- 限流  
end
```

### 深度剖析与缺陷
* **优点**：**绝对精确**。滑动窗口是平滑推进的，彻底杜绝了窗口边界处的突发流量爆表问题。  
* **缺点/致命伤**：  
  1. **内存开销极高（Memory Cost）**：ZSet 必须存下窗口期内的**每一次请求纪录**。如果限流规则是“每小时 10 万次”，意味着一个 Key 的 ZSet 要维持 10 万个 member，不仅极耗内存，还会严重降低 Redis 性能。  
  2. **高并发下的性能瓶颈**：随着 ZSet 规模变大，ZREMRANGEBYSCORE 和 ZCARD 的时间复杂度会升至 $O(\log N + M)$，容易触发 Redis 单线程阻塞。

## 方案二：基于加权估算的近似滑动窗口（Sliding Window Counter）
如果请求量极大（如百万 QPS），方案一的内存占用是不可接受的。此时，业界（如 Cloudflare）更倾向于使用**加权计数器算法**。

### 实现原理
将时间切分为固定大小的窗口（如 1 分钟）。只保留**当前窗口**和**上一个窗口**的简单计数器（Redis String 类型，INCR 递增）。  
假设当前处于第 10:01 分钟的第 15 秒（当前窗口已过去 25%），限制为每分钟 100 次：

* 上一分钟（10:00）的请求数：$Count_{prev} = 80$  
* 本分钟（10:01）截至目前的请求数：$Count_{curr} = 10$

当前滑动窗口内的估计请求数为：

$$\text{Estimated} = Count_{prev} \times (1 - 25\%) + Count_{curr} = 80 \times 0.75 + 10 = 70 \text{ 次}$$  
因为 $70 < 100$，所以允许请求通过；若算出的估计值超出 100 则拒绝。

### 深度剖析与缺陷
* **优点**：**性能极高，内存固定**。每个限流 Key 只需维护两个简单的计数器，空间复杂度为 $O(1)$，即使每秒百万请求，内存消耗也可以忽略不计。  
* **缺点/不足**：  
  1. **存在假设误差**：该算法假设“上一个窗口内的请求分布是均匀的”。如果上一个窗口的所有流量都集中在最后 1 秒发生，估计值会产生偏差，造成**最大 5% 左右的误判率**。  
  2. **无法精细追踪单次请求时点**：它是一个统计估算模型，不适合需要极度精准（如精确到 1 毫秒级防刷）的金融交易场景。

## 总结与选型建议
| 维度 | ZSet 精确滑动窗口 (Sliding Log) | 加权估算滑动窗口 (Sliding Counter) |
| :---- | :---- | :---- |
| **精准度** | 100% 精确 | 近似精确（有微小误差） |
| **内存复杂度** | $O(N)$，与请求次数正相关 | $O(1)$，仅需两个 Counter |
| **时间复杂度** | $O(\log N + M)$，高 QPS 易成为瓶颈 | $O(1)$，性能极高 |
| **适用场景** | 低/中等 QPS、对时间窗口精度要求高的 API（如登录防刷、短信验证码） | 高 QPS、海量流量的微服务网关、API Rate Limit |

如果系统需要**平滑处理突发流量**，且希望请求能被“匀速排队”而非直接拒绝，建议直接评估 **令牌桶（Token Bucket）** 或 **漏桶（Leaky Bucket）** 算法（Redis 官方模块 RedisCell 提供了令牌桶的高性能实现）。

## 补充：加权计数器算法详解

方案二（加权计数器算法）的估算核心建立在一个合理且通用的假设上：假设上一个时间窗口内的流量分布是均匀的。为了让你直观地理解，我们可以把估算过程拆解为“权重推导”与“边界极端情况（缺点）分析”。

### 估算公式拆解

假设我们将固定时间窗口设为 1 分钟（60秒），限流阈值为 100 次。

假设当前时间是 10:01:15（即第 10 分钟已过去 15 秒）：

- 上一个窗口（10:00:00 - 10:00:59）的请求数：记为 $N_{prev} = 80$ 次。
- 当前窗口（10:01:00 - 10:01:15）已发生的请求数：记为 $N_{curr} = 10$ 次。

此时，我们要算的是：从 10:00:15 到 10:01:15 这滑动的一分钟内，到底有多少请求？

#### 权重计算推导

当前窗口已过去的时间比例：

$$\text{Overlap}_{curr} = \frac{15\text{秒}}{60\text{秒}} = 25\%$$

从上一个窗口“借用”的时间比例（也就是滑动窗口与上一窗口重叠的部分）：

$$\text{Weight}_{prev} = 1 - \text{Overlap}_{curr} = 1 - 25\% = 75\%$$

最终估算请求数：

$$\text{Estimated} = N_{prev} \times (1 - \text{Overlap}_{curr}) + N_{curr}$$

$$\text{Estimated} = 80 \times 0.75 + 10 = 70 \text{ 次}$$

因为 $70 < 100$，所以第 11 个请求被允许通过，并将 $N_{curr}$ 更新为 $11$。

### 算法的隐藏缺陷与误差

天下没有免费的午餐。用 $O(1)$ 的内存和 CPU 开销换取高吞吐量的同时，该算法也牺牲了绝对的精确度。

#### 致命假设：上一窗口流量均匀

如果上一窗口的流量分布极不均匀，估算值就会产生误判。

#### 情况 A：误杀（把合规流量错杀）

**场景：** 上一窗口 $N_{prev} = 100$ 次，但这 100 次全部集中在 10:00:00 - 10:00:10（前 10 秒）。到了 10:00:15 - 10:00:59（后 45 秒）完全没有流量。

**实际情况：** 到了 10:01:15 时，前 60 秒内真正的请求数其实只有当前窗口的 $N_{curr} = 10$ 次。

**算法估算：** $100 \times 0.75 + 10 = 85$ 次。算法仍然认为流量很大，留给当前窗口的空间被大幅压缩。

#### 情况 B：漏网（把突发流量放行）

**场景：** 上一窗口 $N_{prev} = 100$ 次，但这 100 次全部集中在 10:00:50 - 10:00:59（最后 10 秒）。

**实际情况：** 到了 10:01:15 时，最近 60 秒内的实际请求数是 $100 + 10 = 110$ 次（已经超限！）。

**算法估算：** $100 \times 0.75 + 10 = 85$ 次（估算值小于 100，继续放行！）。

### 为什么大厂（如 Cloudflare）依然采用它

1. **实际业务中流量是连续且相对平滑的**：在真实的大流量场景（如几万 QPS 的 API）下，很少出现“某 10 秒骤停，下 10 秒暴涨”的极端断层，流量在时间轴上的分布天然趋向均匀。
2. **理论最大误差仅 5% 左右**：数学证明表明，在绝大多数真实流量模型下，加权估算算法的误差率低于 5%。
3. **极低的资源开销**：对于高并发网关来说，用 5% 的微小精度误差，换取 Redis 内存降低 99%、吞吐量提升数倍，这是一个极其划算的工程权衡（Trade-off）。
