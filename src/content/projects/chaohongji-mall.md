这是我在 2025 年 10 月左右参与开发的一套潮宏基会员积分商城后端服务，主要服务于会员端 App 和后台运营管理端。

这个项目的主线不是普通电商里的“商品下单支付”，而是围绕会员积分来做一套兑换闭环：会员登录绑定国家和门店，进入积分商城查看可兑换礼品，用积分下单，系统扣减积分、扣减门店库存、生成兑换码，最后由门店人员完成核销。除了礼品兑换，系统还覆盖优惠券、活动、轮播弹窗、质保单、站内信、会员资料和多国家数据源等能力。

我在这个项目里更多关注的是后端链路能不能跑稳：用户身份怎么传递，国家数据源怎么选，库存怎么防并发扣错，积分和订单状态怎么保持一致，优惠券状态怎么和外部系统同步，后台运营配置怎么影响会员端展示。

## 项目背景

潮宏基这类零售会员业务，线下门店和线上会员系统是连在一起的。用户在线上看积分、领券、兑换礼品，但真正核销和交付往往发生在门店。

这个场景里有几个容易混在一起的问题：

- 会员属于哪个国家、绑定了哪些门店？
- 积分余额来自外部会员系统，商城下单时怎么扣减？
- 礼品库存是总部库存，还是某个门店可兑换库存？
- 用户下单后，门店怎么确认这张兑换码是真的、没被用过？
- 优惠券在本地展示，但外部系统已经使用或过期了怎么办？
- 不同国家的数据源、币种、手机号区号、多语言文案怎么处理？

所以这个项目的核心目标，是把“会员权益”这件事做成一条能落地的链路：会员登录、国家门店绑定、积分查询、礼品展示、积分下单、库存扣减、兑换码生成、门店核销、优惠券同步、后台配置。用户端看起来是几个简单页面，后端实际要把很多业务口径对齐。

## 我的主要工作

这个项目里我主要负责后端接口和业务流程实现，重点在下面几块：

| 方向 | 我做的内容 |
|---|---|
| 会员端接口 | 登录注册、验证码、用户信息、国家列表、门店绑定、币种和手机号区号 |
| 积分商城 | 商城首页、礼品列表、礼品详情、购物车、直接下单、购物车下单 |
| 积分订单 | 订单创建、订单列表、订单详情、积分扣减、订单状态处理 |
| 兑换码核销 | 兑换码生成、二维码生成、门店校验、核销记录、订单完成 |
| 优惠券 | 领券中心、我的优惠券、优惠券二维码、状态校验、傲蓝优惠券同步 |
| 后台运营 | 商品/礼品管理、库存入库、门店库存分配、订单管理、活动、轮播、弹窗、站内信 |
| 多国家数据 | 国家数据源配置、动态数据源切换、国家/门店/币种/多语言相关接口 |
| 工程底座 | Spring Security、JWT、RBAC、统一响应、请求日志、操作日志、文件上传、定时任务 |

项目代码采用 Maven 多模块结构，业务代码主要分在 `system-service` 和 `web-service` 两个服务里。`web-service` 更偏会员端，`system-service` 更偏后台管理端。我的关注点不是把每张表都做一遍增删改查，而是把“后台配置的数据，会员端能正确使用，并且交易链路可追踪”这件事做顺。

## 技术栈和项目结构

后端主要使用 Java 21 + Spring Boot 3.4，数据库访问用 MyBatis-Plus，缓存和登录态用 Redis，接口文档用 SpringDoc / Knife4j。项目里还用了 dynamic-datasource 来处理多国家数据源，使用 Spring Security、JWT 和权限注解做后台权限控制。

项目结构大致是这样：

| 模块 | 说明 |
|---|---|
| `common` | 公共基础能力，比如统一响应、异常处理、Redis、Swagger、MyBatis-Plus、工具类、短信、邮件 |
| `dao` | 数据访问层，放实体、Mapper、XML、枚举、DTO/VO 等共用数据结构 |
| `module` | 可复用能力模块，比如安全认证、外部接口客户端、字段加解密、请求字段解密 |
| `service/system-service` | 后台管理服务，负责商品、礼品、订单、会员、门店、权限、配置等运营能力 |
| `service/web-service` | 会员端服务，负责登录、积分商城、购物车、订单、优惠券、兑换码等 App 接口 |

这样拆的好处是前后台职责比较清楚。会员端接口更关注用户体验和交易流程，后台接口更关注配置、管理、权限和运营动作。公共能力抽到 `common` 和 `module` 后，登录、日志、文件上传、多数据源这些东西不用在每个业务里重复写。

## 核心模块一：会员登录和多国家上下文

会员端第一步是登录和绑定信息。系统支持会员登录、注册、注销、验证码、国家列表、门店列表、手机号区号和币种信息。这里看起来是基础功能，但它会影响后面所有接口。

比如用户进入积分商城时，后端不能只知道“这是哪个用户”，还要知道这个用户当前绑定的国家和门店。因为商品可见范围、库存、积分数据、币种单位、优惠券状态，都可能跟国家和门店有关。

我在这块主要处理了两类上下文：

| 上下文 | 用途 |
|---|---|
| 登录用户上下文 | 从 JWT 中解析用户信息，放到 `UserHolder`，供会员端接口读取 |
| 业务数据上下文 | 根据用户绑定国家和门店，写入 `UserContextUtil`，后续多数据源查询会用到 |

`TokenInterceptor` 会从请求头里取 token，解析 JWT，再把用户信息放进 ThreadLocal。请求结束以后清理上下文，避免串到下一个请求。这个东西写起来不复杂，但如果清理不干净，排查起来会很痛苦，因为表现出来可能是“用户 A 看到了用户 B 的门店数据”。

## 核心模块二：积分商城下单链路

积分商城是项目里最核心的一条业务链路。用户可以从商城首页看推荐礼品，进入礼品列表和详情，也可以直接下单或者从购物车合并下单。

后端下单时要处理的事情比页面看起来多：

1. 校验用户是否登录，以及是否绑定了会员身份。
2. 校验商品存在、已上架，并且当前门店有这个商品。
3. 校验门店剩余库存是否足够。
4. 校验下单时的积分价格和当前门店商品价格是否一致。
5. 用乐观锁扣减门店库存，避免并发下单把库存扣成负数。
6. 创建积分订单和订单明细。
7. 正式环境调用傲蓝积分调整接口扣减积分，测试环境走本地积分记录。
8. 普通礼品生成兑换码，代金券类礼品则走优惠券领取逻辑。

我比较在意的是订单、积分和库存这三件事的关系。订单创建成功但积分没扣，或者积分扣了但库存没扣，都会让后面核销和客服处理变麻烦。所以这块用了事务包住本地订单和库存更新，外部积分扣减失败时也要让订单创建失败，而不是留下一个半成品订单。

## 核心模块三：兑换码生成和门店核销

积分兑换不是下完单就结束。很多礼品需要用户到门店领取，所以系统会在下单成功后生成兑换码，并提供二维码形式给会员端展示。

兑换码这块我主要处理了几个点：

| 问题 | 处理方式 |
|---|---|
| 兑换码不能重复 | 生成时先查重，遇到唯一键冲突会重试 |
| 兑换码不能跨门店乱用 | 核销时校验兑换码绑定的门店 |
| 兑换码不能被伪造 | 生成时保存加密数据，校验时验证完整性 |
| 核销过程要留痕 | 写入兑换记录，记录门店、操作人、核销时间 |
| 核销后订单状态要同步 | 兑换成功后把积分订单状态更新为已完成 |

这块比较适合面试展开，因为它不是单纯的“生成一个随机码”。兑换码本质上是线上订单和线下门店交付之间的凭证，必须考虑重复、篡改、门店权限、状态流转和操作留痕。

## 核心模块四：后台礼品、库存和运营配置

后台管理端主要给运营人员用。这里不只是维护商品标题和图片，还要处理礼品库存、门店分配、上下架、代金券关联、活动、轮播、弹窗、栏目和消息。

礼品库存这块我拆成了两层：

| 库存 | 说明 |
|---|---|
| 商品基础库存 | 总部或待分配库存，表示还有多少可以分到门店 |
| 门店商品库存 | 某个门店已经分配了多少、剩余多少可以兑换 |

后台可以做礼品入库、分配到门店、从门店回收库存。分配时要校验基础库存是否足够；回收时要校验门店剩余库存是否足够；更新库存时也用当前库存值做条件，降低并发修改带来的风险。

另一个细节是商品上下架和购物车的关系。礼品下架或删除时，如果用户购物车里还有这个商品，继续保留只会让后面下单报错。所以更新礼品状态时，会清理相关购物车数据，让会员端看到的状态尽量一致。

## 外部系统对接和数据同步

这个项目对接了傲蓝会员系统。傲蓝主要提供会员积分、优惠券等数据能力，本地商城负责把这些能力包装成会员端能用的业务流程。

积分扣减这块，正式环境会调用傲蓝积分调整接口，把积分扣减同步到外部会员系统；非正式环境则走本地积分记录，方便开发和测试。这里做环境区分，是因为调外部积分接口有真实业务影响，测试环境不能随便动会员积分。

优惠券这块，本地会保存用户优惠券记录，但用户优惠券状态可能会在外部系统发生变化，比如线下已经使用、已过期。我的处理方式是在会员查询优惠券时，同步傲蓝数据，再按可用、已使用、已过期分组返回给前端。如果同步失败，不直接打断用户主流程，而是记录日志并继续使用本地数据。

多国家数据源也是这个项目比较特别的地方。项目里有 `country_my`、`country_th`、`country_kh` 这类国家数据源配置，并且支持动态加载、重载和移除。业务代码通过 `CountryDSService` 这类封装去查不同国家的数据，避免每个业务方法都手写一遍数据源切换。

## 接口安全和后台底座

后台管理端用了 Spring Security、JWT、角色和权限点控制。接口上能看到很多 `@PreAuthorize`，比如商品创建、礼品删除、订单核销这些操作，都不是登录了就能做，还要有对应权限。

项目里还自定义了 JSON 登录过滤器。Spring Security 默认的登录方式更偏表单提交，这里改成从 POST JSON body 里取账号、密码、验证码和 uuid，再交给认证流程处理。这样后台前端调用起来更自然，也更符合现在前后端分离项目的习惯。

此外，系统还做了统一响应、请求日志、操作日志、文件上传、国际化文案、手机号区号、邮件/短信验证码等基础能力。后台系统上线以后，很多问题不是看业务表就能解决的，必须知道“谁在什么时候改了什么配置”，所以操作日志这类能力很实用。

## 我在这个项目里踩过的几个坑

这个项目里有几个点比较适合面试时展开聊。

| 问题 | 当时的处理 |
|---|---|
| 多国家门店 ID 口径不一致 | 会员端返回门店时按本地 `id` 做兼容，避免不同国家 `branchId` 重复影响线上 App |
| 门店库存并发扣减 | 下单和出库时用当前库存做更新条件，更新失败就让用户重试 |
| 订单、积分、库存容易不一致 | 本地订单和库存放进事务，积分扣减失败时中断订单创建 |
| 优惠券本地状态可能滞后 | 查询时同步傲蓝优惠券数据，失败时记录日志，不阻塞主流程 |
| 普通礼品和代金券流程不同 | 普通礼品生成兑换码，代金券关联促销活动并走领券逻辑 |
| 多国家数据源容易写散 | 把数据源切换封装到公共服务和注解里，业务层按国家代码调用 |

这些问题都不算花哨，但很像真实项目里会遇到的东西。会员端只要点一下“兑换”，背后其实牵扯用户、积分、商品、库存、门店、外部系统和订单状态。把这些状态处理清楚，比单纯写几个接口更重要。

## 可以继续优化的地方

如果后续继续迭代，我会优先补三类东西。

第一是交易链路的可观测性。现在已经有日志和订单状态，但还可以把“下单 -> 扣库存 -> 扣积分 -> 生成兑换码 -> 门店核销”的链路做成内部排障视图。客服或运营查问题时，不用在多张表之间来回翻。

第二是积分和库存的自动对账。积分扣减依赖外部系统，库存又在本地维护，长期运行后最好有定时对账和异常单报表，把积分扣减失败、库存扣减失败、订单状态异常这些情况集中暴露出来。

第三是多国家配置文档。国家数据源、币种、手机号区号、门店、语言文案这些配置一多，新国家接入就容易漏步骤。后面可以补一份“新增国家上线 checklist”，减少靠经验记忆。

## 总结

这个项目对我来说，比较有代表性的地方不是技术栈多新，而是它把线上会员权益和线下门店履约连在了一起。

我在里面处理过会员登录、多国家上下文、积分商城下单、库存扣减、兑换码核销、优惠券同步、后台运营配置、权限控制和操作日志。它让我更直观地意识到：会员系统看起来轻，但只要涉及积分、库存和门店核销，后端就必须把状态边界设计清楚。

如果面试里聊这个项目，我会重点讲三件事：积分商城下单链路、兑换码核销和门店库存、多国家数据源与傲蓝系统同步。这三块最能说明我在项目里处理的是业务闭环，而不是简单的接口堆叠。
