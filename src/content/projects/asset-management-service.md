这是我参与开发的一套资管系统后台服务，使用方是国企投资公司的资产管理部门，主要用在投资项目的投后管理里。

这个项目的主线很明确：把企业提供的财报文件通过 OCR 识别出来，落成标准的资产负债表、利润表、现金流量表等结构化数据；然后基于这些数据做公式运算，形成经营指标、评分和评级；最后再结合评级结果，给资产管理人员提供后续管理建议。

围绕这条主线，系统还要处理企业档案、经营监测、任务协作、历史留痕、外部系统对接和接口安全。它不是一个单纯的后台管理 CRUD，真正难的地方在于：财报数据从非结构化文件进入系统以后，后面每一步都要能确认、能追溯、能解释。

## 项目背景

资产管理部门管理的是一批投资项目，每个项目其实就是对应的企业。实际工作里，企业档案、财务报表、经营指标、评级结果、投后任务经常分散在不同文件、表格和系统里。

如果这些东西长期靠人工维护，最直接的问题不是“录入慢”这么简单，而是后面很多判断都缺少统一口径：

- 某一期评级申报到底用了哪些企业资料？
- OCR 识别出来的财报数据有没有经过人工确认？
- 公式计算用的是哪个报表期间、哪个版本的数据？
- 企业现在的数据和历史申报时的数据是不是混在一起了？
- 外部 AI 接口返回了什么，为什么最后落库成这个评分结果？
- 资管任务发给了谁，谁办结了，过程怎么追踪？

所以这个项目的核心目标，是把投后管理里最关键的数据链路串起来：企业建档、财报上传、OCR 解析、结构化入库、指标计算、评分评级、建议输出、任务跟进、历史追溯。这样资产管理人员看到的不只是几张页面，而是一套能支撑投后判断的数据底座。

## 我的主要工作

这个项目里我主要做的是后端服务设计和业务接口实现，重点放在下面几块：

| 方向 | 我做的内容 |
|---|---|
| 企业档案 | 企业基础信息、股东、条款、借担保、文档、大事记等数据维护接口 |
| 经营监测 | 企业树、经营概览、财务指标趋势、三表主要指标查询 |
| 财报 OCR 结构化 | 文件上传、异步识别、草稿保存、人工确认、三表入库、缺失字段导出 |
| 指标计算和评分评级 | 基于财报结构化数据做公式计算、评分明细、评级结果、AI 经营总结和建议落库 |
| 资管任务 | 任务创建、分发、办结、动态、进度统览 |
| 外部对接 | 蓝凌 OA 人员同步、法狗狗 AI OCR/评分/建议生成、启信宝、COS 文件能力 |
| 工程底座 | 接口签名加密、访问控制、操作日志、请求日志、上游 trace 排障 |

项目体量不小，`asset-service` 里有 50 多个控制器，核心业务表也有 30 多张。我的重点不是把每张表都做成 CRUD，而是把几个关键业务流程做顺：尤其是财报 OCR 结构化、财务指标计算、评分评级、历史快照和任务协作。

## 技术栈和项目结构

后端主要是 Java + Spring Boot，数据库用 MySQL，ORM 使用 MyBatis-Plus，同时用 Redis 承担缓存、异步任务状态和临时数据存储。接口文档通过 SpringDoc / Knife4j 提供。

项目采用 Maven 多模块结构：

| 模块 | 说明 |
|---|---|
| `common` | 通用基础能力，比如统一响应、异常处理、MyBatis-Plus、Redis、Swagger、工具类 |
| `module` | 可复用能力模块，比如接口签名加密、访问控制、Excel、登录日志、操作日志、请求日志 |
| `service` | 业务服务，核心模块是 `asset-service` |

`asset-service` 内部再按业务域拆包：

| 包名 | 说明 |
|---|---|
| `asset` | 资管核心业务，包括企业档案、财报、任务、评级 |
| `system` | 用户、角色、菜单、权限、字典、配置 |
| `landray` | 蓝凌 OA 对接 |
| `fagougou` | 法狗狗 AI 对接、异步轮询、财报 OCR 识别、评分评级和经营建议 |
| `ops` | 内部排障页面和上游 trace 查询 |

这样拆的好处是，业务代码和通用能力不会全部挤在一个模块里。像接口加密、访问控制、Excel、日志这些能力，不只资管业务会用，单独放在 `module` 里更清楚。

## 核心模块一：企业档案和经营监测

企业档案是系统的数据底座。

这里不仅有企业名称、行业、统一社会信用代码这些基础字段，还包括股东信息、委派董事、关键条款、回购条款、特殊合同、企业文档、大事记等。资管系统里的企业档案，不是简单展示工商信息，而是后面经营监测、评级申报、任务协作都会引用的主数据。

经营监测这块主要处理财务和经营指标，包括资产负债、利润、现金流，以及偿债能力、盈利能力、营运能力、发展能力等指标。后端要支持企业树、行业筛选、周期筛选、趋势图、排名等查询方式。

这里我比较注意的是接口的复用性。比如页面上展示的是一个经营概览，但后端不能只为这个页面拼一个临时接口，否则后面换一个维度就要重写。能抽成按企业、周期、指标查询的地方，我尽量让它保持可组合。

## 核心模块二：资管任务工作台

资管任务工作台解决的是协作问题。

系统支持任务状态统计、任务列表、任务进度统览、新建任务、办结任务、任务动态、编辑和删除。这个模块看起来像普通任务管理，但在资管场景里，它还要关联企业、接收人、子企业执行情况和历史任务。

我在这个模块里主要处理两个点：

1. 任务不是只有一条记录，还要能看推进过程。
2. 主任务和子企业执行情况要分得清，不然后续看进度会很乱。

这类模块的难点不在技术概念，而在业务状态设计。状态设计得含糊，后面页面展示、权限判断、删除校验都会变复杂。

## 核心模块三：财报 OCR 结构化入库

财报 OCR 是这个项目最核心的一条链路。资产管理人员拿到的财报，很多时候不是天然可计算的数据，而是 PDF、图片扫描件、Excel 或文件 URL。系统要做的第一件事，就是把这些文件里的资产负债表、利润表、现金流量表识别出来，转换成后续可以计算、可以查询、可以追溯的标准结构化数据。

后端收到文件以后，不会同步等待 OCR 和 AI 解析结果，而是走异步任务：

1. 创建本系统的本地任务 `taskId`，先把这次处理记录下来。
2. 上传文件，或者解析前端传入的文件 URL。
3. 提交给法狗狗 AI，拿到上游任务 ID。
4. 定时轮询上游进度，避免接口长时间阻塞。
5. 上游完成后拉取 OCR 和财报解析结果。
6. 对返回结果做字段映射、报表期间识别、年报/季报口径处理。
7. 先保存为草稿，不急着写正式业务表。
8. 用户核对确认后，再写入资产负债表、利润表、现金流量表等标准表。

这里我没有把 AI 返回结果直接当成最终数据。财报是后续评分评级的基础，如果源头数据错了，后面的公式计算、经营评价和建议都会跟着偏。所以我在链路里保留了“草稿确认”这一步，让 OCR 识别结果先进入可编辑、可核对的中间状态，确认以后再成为正式数据。

这个流程里，我重点处理了几个真实问题。

| 问题 | 处理方式 |
|---|---|
| OCR 和上游解析耗时长 | 本地任务 + 上游任务 + 定时轮询，不阻塞请求 |
| OCR/AI 返回结果不能直接入库 | 先保存草稿，让用户确认后再写正式三表 |
| 年报和季报口径不同 | 增加年报标识和报表期间处理逻辑 |
| 字段识别不完整 | 支持缺失字段导出，方便人工核对 |
| 出问题不好排查 | 保存上游 trace，可追溯原始响应和映射结果 |
| 服务重启后任务丢失 | 做异步任务恢复和状态存储 |

这块如果面试展开，我会重点讲三个点：为什么不能同步调 OCR 接口，为什么 OCR 结果要先走草稿确认，为什么要保留上游 trace。因为这几个问题都来自真实业务，不是单纯写一个上传接口就能解决的。

## 核心模块四：指标计算、评分评级和历史快照

财报数据结构化以后，下一步就是让这些数据真正参与业务判断。系统会基于资产负债表、利润表、现金流量表里的字段做公式运算，生成偿债能力、盈利能力、营运能力、发展能力等指标，再把这些指标带入评分评级流程。

这部分我重点关注的是数据口径。评分评级不是页面上展示一个分数就结束了，它需要回答几个问题：

- 这次评分用了哪一期财报？
- 每个指标的原始数据来自哪里？
- 公式计算结果和最终分数能不能追溯？
- 后续企业档案或财报被修改，会不会影响历史评级？
- 给出的经营建议是基于哪次评分结果生成的？

所以在设计上，我把评分评级拆成了几层：企业当前主数据、财报结构化数据、公式计算结果、评分明细、评级结果、经营总结和建议。这样每一层都有自己的职责，后续排查时也能顺着链路往前找。

历史快照是这里比较重要的设计。一开始最容易出现的问题是：历史详情如果继续读取当前企业档案，就会出现数据“穿越”。比如今天修改了企业股东，去年那次评级申报详情也跟着变了。用户明明在看历史记录，但页面展示的是当前主数据。

为了解决这个问题，我把评分评级申报分成两类数据：

| 数据 | 用途 |
|---|---|
| 当前企业主数据 | 新建和编辑申报时使用，代表企业当前状态 |
| 申报快照 | 历史详情使用，代表当时提交时的状态 |

申报时，系统会把企业信息、股东、条款、借担保、经营情况等主体信息保存为快照。评分明细、附加分、评级结果、AI 经营总结和后续建议，则和当次评分记录绑定。这样后面再打开历史详情，看到的是当时那次申报的完整上下文，而不是被当前数据污染后的结果。

这个设计解决的是历史一致性问题。对投后管理系统来说，这一点很重要，因为评级本身就是阶段性判断，不能被后续主数据修改影响。

## 外部系统对接和排障

这个项目对接了几类外部能力。

蓝凌 OA 主要用于人员同步。内部系统不能长期自己维护一套人员数据，否则和 OA 不一致以后，权限、任务接收人、消息通知都会出问题。

法狗狗 AI 是财报 OCR、经营总结和评分评级的重要来源，参与文件识别、字段抽取、能力指标、附加分、经营建议等流程。这里我没有只做“调用接口然后落库”，而是加了上游 trace。

trace 主要记录：

- 本系统任务 ID
- 上游任务 ID
- 请求/响应摘要
- 上游原始返回
- 字段映射后的结果
- 对应企业和报表期间

这样做的好处是，后续如果业务问“这个字段为什么没识别出来”“这个评分为什么是这样”，我可以查到上游到底返回了什么，而不是只能猜。

## 接口安全和后台底座

资管系统涉及企业档案、财务数据和评级结果，所以接口安全不能只靠登录态。

项目里除了 Spring Security、JWT、角色权限、接口权限之外，还接了接口签名加密模块。大致流程是：

1. 客户端先做密钥交换。
2. 请求携带时间戳、nonce、key version、fingerprint 和签名。
3. 服务端先验签，再解密请求体。
4. 业务处理完成后，响应体可以加密，并附带响应签名。
5. nonce 在时间窗口内只能使用一次，降低重放风险。

这套方案不能替代 HTTPS，但可以在 HTTPS 之外增加一层防篡改、防重放和敏感 JSON 保护。

此外，项目还做了 IP 黑白名单、访客封禁、登录日志、请求日志、操作日志。后台系统一旦上线，排查问题时不能只看业务表，必须能回答“谁在什么时候做了什么”。

## 我在这个项目里踩过的几个坑

这个项目里有几个问题比较适合面试时展开聊。

| 问题 | 当时的处理 |
|---|---|
| 历史申报被当前主数据影响 | 增加申报快照，历史详情读取快照而不是 live 数据 |
| OCR/AI 识别结果不稳定 | 草稿确认 + 缺失字段导出 + trace 留痕 |
| 异步任务链路长 | 本地任务状态、上游任务 ID、定时轮询、任务恢复 |
| 页面维度变化快 | 查询服务尽量按企业、周期、指标等维度抽象，不完全绑定单一页面 |
| 外部系统问题难定位 | 保存上游原始响应和映射快照，提供内部排障接口 |
| 安全要求高 | JWT/RBAC 基础上增加接口签名、请求体加密、响应签名、防重放 |

这些问题都不是很“炫”的技术点，但很贴近真实业务系统。我的理解是，后端开发的价值不只是把接口写出来，而是让数据流转以后还能对得上、查得到、出问题能定位。

## 可以继续优化的地方

如果后续继续迭代，我会优先补三类东西。

第一是项目文档。现在很多业务规则藏在接口注解、service 逻辑和 migration 里，对新人不够友好。可以补一份启动说明、模块说明和核心流程图。

第二是测试样例。财报 OCR、字段映射、公式计算和评分评级都很适合沉淀一批样例文件、样例响应和断言。上游接口或公式口径一变，能更早发现影响范围。

第三是可观测性。现在已经有 trace 和日志，但还可以进一步做任务链路视图，把“本地任务 -> 上游任务 -> 草稿 -> 确认入库”的过程展示得更直观。

## 总结

这个项目对我来说，比较有代表性的地方不是用了多少框架，而是它覆盖了一个后台系统从业务建模到工程落地的很多环节。

我在里面处理过主数据、财报 OCR 结构化、公式计算、历史快照、异步任务、AI 结果确认、外部系统对接、接口安全和排障留痕。它让我更清楚地意识到：后端开发不只是写接口，还要考虑数据口径、流程边界、异常恢复和后续排查。

如果面试里聊这个项目，我会重点讲三件事：财报 OCR 结构化入库、指标公式计算和评分评级、接口安全与 trace 排障。这三块最能说明我在这个项目里解决的不只是 CRUD，而是真实业务系统里的复杂问题。
